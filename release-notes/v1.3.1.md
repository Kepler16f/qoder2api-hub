# v1.3.1 — 上游传输韧性修复

本版本修复**上游连通性被本地代理状态绑架**导致的一类顽固故障：表现为网关持续报 `transport transient: <urlopen error [WinError 10061] 由于目标计算机积极拒绝>`，客户端拿到 502，且开关系统代理、改注册表都无法恢复，只能重启进程。

网关本体版本 1.2.17 → 1.2.18，纯传输层修复，协议零改动。

## 🐛 问题修复

- **修复出站 opener 缓存冻结代理决策**：`urllib` 的默认 opener 在进程首次请求时构建一次并缓存到进程结束，会把启动那一刻的系统代理设置（如 Clash 的 `127.0.0.1:7890`）永久带进后续所有上游请求——代理软件随后退出或换端口时，上游调用会一直撞死在死端口上（WinError 10061），用户侧任何开关操作都无效。现改为**逐请求实时解析代理状态**（`UpstreamOpener`，qoder_accounts.py），覆盖全部上游调用点（聊天、模型发现、openapi、设备授权轮询）。三种出站形态可随时切换、无需重启进程：
  - **TUN 模式**（FlClash 等）：系统代理开不开都行，流量在网络层被透明接管
  - **系统代理（无 TUN）**：开关状态对下一个请求立即生效
  - **完全直连**：无代理环境不受影响
  - 特殊部署可用 `QD_PROXY_UPSTREAM_PROXY`（如 `http://127.0.0.1:7890`）显式钉死代理

- **修复全池传输故障下代理过早放弃**：原来单账号瞬时重试 2 次（1s/2s 退避）、逐号轮换约 30 秒即向客户端返回 502，扛不过上游 1 分钟级别的拒连/断流风暴（实测 2026-10-06 19:25 窗口全池 10061）。现在全部账号均因传输层故障失败时，退避 15 秒后**整池重扫**（最多 2 轮，`UPSTREAM_MAX_SWEEPS`/`UPSTREAM_SWEEP_WAIT`），把上游瞬时抖动挡在代理内侧；重扫期间一旦出现 HTTP 响应或频控，说明上游已恢复，立即按既有语义上抛，不改变 401/429/4xx 的处理路径。

## ✅ 验证

- 行为测试：默认形态连通、显式死代理复现 10061、进程内注入死系统代理→下一个请求立即恢复（旧代码需重启）、清除后即时恢复
- 无头冒烟（`--smoke-test`）：health / models / dashboard 全绿
